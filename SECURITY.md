# Аудит безопасности ChemCalc

Дата проверки: 17 ноября 2026 г.  
Область: серверный код, авторизация, роли, статика, API сообщества, загрузки, SQL-слой, CSRF и маршруты.  
Формат: ручной code review + автоматические тесты. Это не полноценный внешний пентест и не заменяет проверку инфраструктуры Render/Supabase.

## 1. Краткий итог

Проверка выявила **критическую утечку исходников через статический сервер** и **высокую проблему с отдачей SPA-заглушки для несуществующих путей**. Обе проблемы исправлены, добавлена кастомная страница 404 и регрессионные тесты.

SQL-инъекций не найдено: пользовательские значения передаются параметрами, динамические имена таблиц/колонок формируются только внутренним кодом. Повышения привилегий через регистрацию, профиль или скрытые страницы не обнаружено.

## 2. Найденные проблемы

## 3. SQL-инъекции

Проверены все вызовы `prepare`, `query`, `exec` и динамическое построение SQL.

**Результат: SQL-инъекций не обнаружено.**

Меры, которые уже работают:

- значения логина, пароля, тегов, статусов, голосов, профилей, заявок и вопросов передаются как параметры `?`/`$n`;
- `ORDER BY` выбирается только из фиксированного списка (`score`, `recent`, `reputation`), а не из query-параметра;
- `WHERE` для фильтров собирается из статических фрагментов, значения — параметры;
- динамические идентификаторы (`uploads.question_id`/`answer_id`, таблицы при обезличивании) задаются внутренним кодом, а не пользователем;
- SQLite использует подготовленные выражения, PostgreSQL — параметризованные запросы;
- ошибки БД не возвращают SQL-текст клиенту.

Проверенные payload-ы:

```text
login: creator' OR '1'='1
tag:   " OR 1=1--
status: pending' OR 1=1--
sort:  score; DROP TABLE users--
```

Все запросы завершились штатно, без 500 и без выполнения внедрённого SQL.

## 4. Повышение привилегий

### Регистрация

`POST /api/auth/register` всегда записывает `privileges = 'basic'`. Поля `privileges`, `id`, `role` из тела игнорируются. Проверено тестом: пользователь, отправивший `privileges: "GOD"` и `id: 1`, получает роль `basic` и новый id.

### Профиль

`PATCH /api/auth/profile` принимает только никнейм, аватар и приватность. Логин и роль изменить нельзя. Даже при передаче `privileges: "GOD"` роль остаётся прежней.

### Роли

- `GET /api/users` — только `GOD`;
- `PATCH /api/users/:id/role` — только `GOD`;
- назначить можно только `basic`, `admin`, `admin+`;
- роль `GOD` нельзя назначить через API и нельзя изменить у текущего GOD;
- модерация вопросов/ответов/комментариев требует `admin`, `admin+` или `GOD`;
- ревью заявок требует `admin+`/`GOD`; автор не может подтвердить собственную заявку, кроме GOD-исключения.

### Приватность

Приватный профиль (`privacy = 'private'`) отдаётся только владельцу или GOD. Анонимный и другой обычный пользователь получают 403. Проверено.

### Скрытые страницы и панели

Скрытые вкладки в интерфейсе (управление пользователями, danger zone и т.п.) не являются границей безопасности: все соответствующие API защищены сервером. После исправления S-02 неизвестные пути вроде `/admin` отдают 404, а не оболочку приложения.

## 5. Защитные заголовки

Добавлены:

```text
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: camera=(self), microphone=(), geolocation=()
Cross-Origin-Opener-Policy: same-origin-allow-popups
Content-Security-Policy: frame-ancestors 'self' https://web.telegram.org https://*.telegram.org; base-uri 'self'; object-src 'none'
Strict-Transport-Security: max-age=31536000; includeSubDomains   (production/HTTPS)
```

CSP намеренно ограничен: inline-скрипты Telegram SDK и существующая архитектура не позволяют сразу включить строгий `script-src` без отдельного этапа.

## 6. CSRF, cookie и сессии

- Все изменяющие API требуют CSRF-токен и cookie сессии.
- CSRF-токен сравнивается через `timingSafeEqual`.
- `Origin`, если передан, должен совпадать с `Host`; malformed Origin отклоняется как 403.
- Cookie сессии: `HttpOnly`, `SameSite=Lax`, `Secure` в production, TTL 30 дней с продлением.
- Пароли хранятся как scrypt-хэши; plaintext не сохраняется.
- Повреждённая cookie игнорируется, а не вызывает 500.

## 7. Статика и 404

- Введён allowlist: `index.html`, `404.html`, `styles.css`, `sw.js`, manifest, `js/`, `data/`, `vendor/`, `icons/`, `LICENSES/`.
- `server/`, `scripts/`, `tests/`, `node_modules/`, `var/`, `.git/`, `.env`, `GOD.txt`, `package.json`, `server.mjs` недоступны.
- Path traversal и encoded traversal (`%2e%2e`) отклоняются.
- Несуществующий путь отдаёт **HTTP 404** и кастомную страницу `404.html`.
- `/api/*` для неизвестного маршрута по-прежнему отдаёт JSON 404.

Кастомная страница: тёмная химическая тема, колба, анимация, кнопки «На главную», «В сообщество», «Назад», отображение запрошенного пути. Проверена на 1200×900 и 390×844, без горизонтального переполнения.

## 9. Остаточные риски и рекомендации

1. **Rate limit за прокси.** Использовать доверенный `X-Forwarded-For` (только от Render) или отдельный лимитер по IP+аккаунту. Иначе возможен как общий лимит на всех, так и обход при прямом доступе.
2. **GOD без MFA.** Добавить TOTP/резервные коды и сократить срок жизни сессии для GOD.
3. **Публичные вложения.** Не загружать паспорта, медицинские документы и коммерческие тайны; при необходимости сделать приватные вложения с проверкой доступа.
4. **CSP.** Постепенно вынести inline-скрипты, добавить nonce/hash и включить `script-src`.
5. **Секреты.** Если `GOD.txt` или `.env` когда-либо попадали в публичный деплой/репозиторий — сменить пароль GOD и ключи (Telegram, БД) и проверить логи.
6. **Мониторинг.** Добавить алерты на 5xx, всплеск 401/403/429 и аномальные запросы к статике.
7. **Внешний пентест.** Провести после стабилизации платежей/школ; текущий аудит — внутренний code review.

## 10. Что не проверялось

- сетевая инфраструктура Render/Supabase и их ACL;
- DDoS-устойчивость;
- реальные Telegram-клиенты и iframe-политики;
- юридическая соответствие политики конфиденциальности;
- бинарный анализ браузера и сторонних SDK.

## 11. Поддержка

Сервис поддержки использует те же аккаунты и роли, но является отдельной приватной зоной:

- пользователь видит только свои обращения; чужие `thread_id` дают 404;
- очередь `/api/support/*?scope=inbox` доступна только `admin+` и `GOD`;
- закрытие, удаление спама и назначение проверяются на сервере, а не только в UI;
- внутренние заметки не попадают в ответы пользователю;
- фото поддержки приватные: отдельная таблица, проверка автора/агента, `Cache-Control: private, no-store`, проверка сигнатуры PNG/JPEG/WebP;
- все изменяющие запросы требуют CSRF;
- есть rate limit на обращения, сообщения и фото;
- soft delete скрывает спам из пользовательской выдачи, GOD может восстановить;
- `tests/support-api.test.js` проверяет доступ, роли, внутренние заметки, закрытие, удаление и приватные вложения.
