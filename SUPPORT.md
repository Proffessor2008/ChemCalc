# Сервис поддержки ChemCalc — концепция

**Статус: MVP реализован в v68. Документ описывает архитектуру и дальнейшее развитие.**

В текущем MVP сервис открывается полноэкранным разделом из настроек; отдельный URL `/support` зарезервирован для следующего этапа. Очередь поддержки доступна тем же ролям `admin+` и `GOD`.

Цель — встроенная поддержка, которая ощущается как отдельный сервис, но использует те же аккаунты, роли, сессии и никнеймы, что и ChemCalc. Пользователь открывает её из настроек; администраторы `admin+` и `GOD` работают с обращениями в отдельной очереди.

## 1. Главное решение

Не делать отдельный микросервис с собственными аккаунтами на первом этапе. Рекомендуемая схема:

**модульный монолит + отдельный раздел `/support` + отдельная очередь `/support/inbox`.**

Это даёт:

- единый аккаунт и сессию без SSO и дублирования паролей;
- мгновенную синхронизацию ролей и никнеймов;
- одну транзакционную БД: удаление аккаунта, блокировка, смена роли сразу видны в поддержке;
- меньше поверхности для утечек и CSRF/CORS-ошибок;
- возможность позже вынести поддержку в отдельный сервис через API, не меняя пользовательский сценарий.

Если понадобится именно отдельный домен/деплой, то только через SSO: одноразовый подписанный тикет, обмен на короткоживущую сессию поддержки и общий идентификатор пользователя. Это отдельный проект, не первый этап.

## 2. Пользовательский сценарий

1. Пользователь открывает **Настройки**.
2. Внизу видит кнопку **«Поддержка»** с иконкой чата/спасательного круга.
3. Если есть непрочитанные ответы — badge с числом.
4. Открывается `/support` — раздел «Мои обращения»:
   - список обращений со статусом и последним сообщением;
   - кнопка **«Новое обращение»**;
   - пустое состояние с объяснением, когда писать в поддержку.
5. Новое обращение:
   - выбор темы (категории);
   - краткий заголовок;
   - описание;
   - до 3–5 фото;
   - кнопка «Отправить».
6. После создания — экран «Обращение №SC-2026-000123 создано», статус «Открыто», ориентировочное время ответа.
7. Ответы приходят в чат обращения и в уведомления; в Telegram — уведомление со ссылкой, без вложения и без текста с персональными данными.
8. Пользователь видит никнейм ответившего администратора и его роль (`admin+`/`GOD`), дату и статус.
9. Пользователь может отвечать, пока обращение не закрыто. Закрывает только администратор.

### Категории (суть вопроса)

Обязательный выбор одной категории; от неё зависит подсказка и дополнительные поля.

| Ключ | Название | Что уточнять |
|---|---|---|
| `bug` | Ошибка в программе | что делали, что ожидали, что получилось, устройство/браузер, скриншот |
| `calculation` | Вопрос по расчёту/химии | уравнение/задача, ожидаемый ответ, скриншот результата |
| `account` | Аккаунт, вход, Telegram | логин/никнейм, способ входа, текст ошибки |
| `export` | PDF/DOCX и печать | формат, справочник, страница, скриншот |
| `community` | Сообщество и модерация | ссылка на вопрос/ответ, что нарушено |
| `billing` | Оплата и подписка (позже) | план, чек, дата, последние 4 цифры (не полный номер карты) |
| `idea` | Предложение | что улучшить и зачем |
| `other` | Другое | свободное описание |

Категории хранятся в БД/конфиге, чтобы их можно было менять без релиза. Для каждой — свои placeholder-ы и минимальная длина описания.

### Ограничения пользователя

- Нельзя создавать обращения чаще лимита (например, 5 в сутки, 20 в месяц).
- Нельзя прикреплять исполняемые файлы, SVG, HTML, архивы.
- Нельзя видеть чужие обращения.
- Нельзя удалять обращение после ответа администратора; можно попросить закрыть/удалить.
- Нельзя закрыть обращение — только пометить «Мне помогло» / «Вопрос решён», после чего администратор закрывает.
- Закрытое обращение read-only; новый вопрос — новое обращение. Опционально: ответ пользователя в течение 14 дней автоматически переоткрывает обращение.

## 3. Сценарий администратора

`admin+` и `GOD` видят в основном приложении пункт **«Поддержка»** с очередью, либо отдельный `/support/inbox`.

Экран очереди:

- фильтры: новые, мои, без ответа, ждут пользователя, решённые, закрытые, спам;
- поиск по номеру, нику и тексту;
- сортировка по SLA/последнему сообщению/приоритету;
- счётчики по категориям;
- карточка: номер, никнейм, роль, категория, возраст, последний ответ, assigned.

Экран обращения:

- чат с пользователем;
- никнейм и роль каждого автора;
- внутренние заметки (пользователь не видит);
- быстрые ответы;
- вложения с превью;
- действия: ответить, взять в работу, переназначить (GOD), закрыть, удалить спам, восстановить (GOD);
- история изменений статуса;
- карточка пользователя: логин, никнейм, роль, дата регистрации, Telegram, число обращений, репутация.

### Матрица прав

| Действие | basic | admin | admin+ | GOD |
|---|---:|---:|---:|---:|
| Создать своё обращение | да | да | да | да |
| Читать своё обращение | да | да | да | да |
| Читать все обращения | нет | нет | да | да |
| Отвечать пользователю | только своё | только своё | да | да |
| Внутренние заметки | нет | нет | да | да |
| Удалить спам | нет | нет | да | да |
| Восстановить удалённое | нет | нет | нет | да |
| Закрыть/решить | нет | нет | да | да |
| Переназначить | нет | нет | да | да |
| Менять категории | нет | нет | нет | да |
| Экспорт аудита | нет | нет | нет | да |

`admin` специально не получает доступ к поддержке, чтобы соответствовать требованию «admin+ и GOD». Если позже нужен read-only для admin — это отдельное решение.

## 4. Модель данных

### `support_threads`

```text
id                 UUID PK
number             TEXT UNIQUE        -- SC-2026-000123
author_id          FK users
category           TEXT               -- bug/calculation/...
subject            TEXT
status             TEXT               -- new/open/waiting_user/resolved/closed/deleted
priority           TEXT               -- low/normal/high/urgent
assigned_to        FK users NULL
created_at         TEXT
updated_at         TEXT
last_message_at    TEXT
closed_by          FK users NULL
closed_at          TEXT
resolution_note    TEXT
deleted_by         FK users NULL
deleted_at         TEXT
delete_reason      TEXT
spam_score         REAL DEFAULT 0
```

### `support_messages`

```text
id                 UUID PK
thread_id          FK support_threads ON DELETE CASCADE
author_id          FK users
body               TEXT
visibility         TEXT               -- public/internal
created_at         TEXT
edited_at          TEXT
deleted_at         TEXT
deleted_by         FK users NULL
```

### `support_attachments`

```text
id                 UUID PK
message_id         FK support_messages ON DELETE CASCADE
thread_id          FK support_threads ON DELETE CASCADE
uploader_id        FK users
filename           TEXT
mime               TEXT               -- image/png, image/jpeg, image/webp
size               INTEGER
width/height       INTEGER
sha256             TEXT
data               BLOB/BYTEA         -- или приватный storage key
created_at         TEXT
scan_status        TEXT               -- pending/clean/rejected
```

Ключевой момент: **вложения поддержки приватные**. Нельзя переиспользовать публичный `/api/uploads/:uuid`. Нужен отдельный авторизованный endpoint, который проверяет, что запрашивающий — автор обращения или `admin+`/`GOD`.

### `support_events`

```text
id, thread_id, actor_id, action, from_value, to_value, note, created_at
```

Действия: created, assigned, status_changed, closed, reopened, deleted, restored, internal_note_added.

### `support_notifications` или расширение `notifications`

Текущая `notifications` привязана к `proposal_id`. Для поддержки лучше добавить nullable `support_thread_id` и тип `support_reply/support_status/support_assigned`, либо отдельную таблицу. В UI — единый колокольчик.

### Индексы

- `support_threads(status, last_message_at DESC)`
- `support_threads(author_id, last_message_at DESC)`
- `support_threads(assigned_to, status)`
- `support_messages(thread_id, created_at)`
- `support_attachments(thread_id)`
- полнотекстовый индекс по subject/body (Postgres FTS; SQLite — FTS5 или LIKE на первом этапе).

## 5. API

Пользовательские:

```text
GET    /api/support/categories
POST   /api/support/threads
GET    /api/support/threads?scope=mine&status=...
GET    /api/support/threads/:id
POST   /api/support/threads/:id/messages
POST   /api/support/threads/:id/helpful     -- «мне помогло», не закрывает
GET    /api/support/attachments/:id         -- авторизованно, private/no-store
```

Административные (`admin+`/`GOD`):

```text
GET    /api/support/inbox?status=&category=&assigned=&q=
POST   /api/support/threads/:id/assign
POST   /api/support/threads/:id/close
POST   /api/support/threads/:id/reopen
DELETE /api/support/threads/:id             -- soft delete, причина
POST   /api/support/threads/:id/restore     -- GOD
GET    /api/support/threads/:id/events
```

Общие правила:

- все изменяющие запросы — с CSRF и проверкой роли на сервере;
- авторство и доступ проверяются по `thread_id`, а не только по UI;
- чужие обращения → 404 (не подтверждать существование);
- вложения — отдельная проверка доступа;
- idempotency key для создания/ответа, чтобы двойной клик не создал дубль;
- rate limit на создание/ответы/вложения;
- SSE-события `support:new`, `support:message`, `support:status` для очереди и чата; fallback polling.

## 6. Синхронизация аккаунтов

- Один `users` и одна сессия. Отдельной регистрации в поддержке нет.
- Никнейм: `nickname || login`; при смене никнейма новые сообщения показывают актуальный, старые — текущий (или snapshot для аудита).
- Роль проверяется при каждом запросе, а не кэшируется в UI.
- Если пользователь потерял роль `admin+`, доступ к очереди пропадает сразу; его назначенные обращения остаются, GOD может переназначить.
- Если аккаунт удалён: профиль обезличивается, сообщения отображаются как «Удалённый пользователь», вложения удаляются по политике хранения.
- Telegram-аккаунт синхронизируется так же: `telegram_id` уже есть в `users`; отдельной привязки к поддержке не нужно.
- В ответе администратора показываются никнейм и бейдж роли; в карточке пользователя — логин/никнейм, чтобы администратор понимал, кто пишет.

## 7. Статусы и жизненный цикл

```text
new → open (взят в работу) → waiting_user → resolved → closed
  ↘ deleted (спам/реклама) ↗ restore (GOD)
```

- `new` — создано пользователем, ещё никто не ответил.
- `open` — администратор взял в работу/ответил.
- `waiting_user` — администратор ждёт ответа пользователя.
- `resolved` — администратор отметил решённым; пользователь видит «решено», может ответить/поблагодарить.
- `closed` — финальное закрытие только `admin+`/`GOD`; read-only.
- `deleted` — soft delete для спама; скрыто из пользовательской выдачи, но доступно GOD в аудите.
- Ответ пользователя в `resolved` в течение 14 дней может вернуть `open`.
- Автозакрытие `resolved` через 7 дней без ответа — только если это разрешено правилами; фиксировать как действие системы в audit.

## 8. Уведомления

- Пользователю: ответ администратора, смена статуса, закрытие.
- Администраторам: новое обращение, ответ пользователя, назначение.
- В приложении — счётчик и список.
- Telegram — короткое уведомление со ссылкой на обращение; без текста вложения и без чувствительных деталей.
- Email — позже, если появится почтовый канал.
- Не отправлять уведомления о внутренних заметках.

## 9. Безопасность и приватность

- Поддержка — приватная зона; никакой публичной выдачи и sitemap.
- Вложения: только изображения PNG/JPEG/WebP, до 5 МБ, до 5 на сообщение; проверка MIME по сигнатуре, пережатие, удаление EXIF.
- Отдача вложений: `Cache-Control: private, no-store`, `Content-Disposition: inline` только для изображений, проверка участия в обращении.
- Текст — plain text/Markdown с экранированием; никакого raw HTML.
- Внутренние заметки не попадают в API пользователя.
- Аудит: кто закрыл/удалил/переназначил, когда и почему.
- Ограничения: rate limit, антиспам, блокировка пользователя, проверка дублей.
- Удаление аккаунта не удаляет историю поддержки мгновенно: она нужна для разбора и юридических obligations; политика хранения и обезличивания должна быть описана в документах.
- Не логировать тела обращений в обычные логи; только ID/статусы/ошибки.
- GDPR/152-ФЗ: экспорт и удаление по запросу; срок хранения (например, 12 месяцев после закрытия) утвердить.

## 10. UX-детали

### Настройки

Кнопка «Поддержка» внизу настроек, рядом с юридическим документом, с иконкой и badge непрочитанных. Не прятать в глубину.

### Пользователь

- Список карточек: номер, тема, статус, последний ответ, дата.
- Чат с системными сообщениями: «Иван (admin+) взял обращение», «Закрыто».
- Вложение — превью, клик открывает просмотр.
- Статусные цвета: new — акцент, open — синий/teal, waiting — amber, resolved — green, closed — muted, deleted — red.
- Кнопка «Мне помогло» не закрывает обращение.
- Пустые состояния и понятные ошибки.

### Администратор

- Desktop: три колонки — очередь, чат, карточка пользователя.
- Mobile: очередь → чат, карточка сворачивается.
- Быстрые ответы по категориям.
- Внутренняя заметка — переключатель «Пользователь не увидит».
- Удаление спама — с причиной и подтверждением; восстановление только GOD.
- Закрытие — с итоговым комментарием, который увидит пользователь.
- Показывать SLA-таймер и просрочку.

## 11. Метрики

- время первого ответа (FRT);
- время решения;
- доля просроченных SLA;
- reopen rate;
- CSAT после закрытия;
- распределение по категориям;
- число спам-удалений;
- нагрузка на администратора;
- доля обращений, решённых без эскалации.

## 12. Краевые случаи

- Пользователь удалил аккаунт во время открытого обращения — сообщения остаются, автор «Удалённый пользователь», новые ответы недоступны.
- Администратор потерял роль — доступ сразу закрыт; назначенные обращения переназначает GOD.
- Два администратора одновременно закрывают — первый выигрывает, второй получает 409.
- Пользователь отвечает после закрытия — 409, предложить новое обращение.
- Повторная отправка — idempotency key.
- Вложение не прошло проверку — сообщение не создаётся или создаётся без файла с ошибкой.
- Спам-удаление скрывает обращение из очереди, но оставляет audit для GOD.
- Поиск не должен показывать внутренние заметки обычному пользователю.
- IDOR: подмена `thread_id`/`attachment_id` → 404.
- Копирование ссылки на обращение другим пользователем → 404.
- Telegram без `initData`/сессии → обычный вход, поддержка доступна после логина.

## 13. Этапы, если идея будет одобрена

### Этап 1 — MVP

- таблицы threads/messages/attachments/events;
- `/support` для пользователя и `/support/inbox` для admin+/GOD;
- категории, текст, фото;
- ответы, закрытие, soft delete;
- уведомления в приложении;
- аудит;
- тесты доступа (IDOR, роли, CSRF, приватные вложения).

### Этап 2 — удобство

- внутренние заметки, назначение, быстрые ответы;
- фильтры/поиск/SLA;
- Telegram-уведомления;
- CSAT;
- шаблоны категорий.

### Этап 3 — масштабирование

- отдельный домен/SSO, если реально нужно;
- экспорт, аналитика, интеграция с почтой;
- платежи/подписки в поддержке.

## 14. Открытые вопросы

1. Кто именно закрывает: только `admin+` и `GOD` или ещё `admin`?
2. Кто удаляет: `admin+` и `GOD` или любой модератор?
3. Может ли пользователь закрыть своё обращение или только пометить «решено»?
4. Нужен ли отдельный домен или достаточно `/support`?
5. Сколько хранить закрытые обращения и вложения?
6. Нужны ли email-уведомления или только in-app/Telegram?
7. Нужна ли оценка CSAT после закрытия?
8. Должны ли старые сообщения показывать никнейм на момент отправки или текущий?

## 15. Что не делать в MVP

- отдельный микросервис с собственной БД и аккаунтами;
- публичные ссылки на обращения;
- свободный HTML в сообщениях;
- вложения любых типов и без проверки;
- автоматическое закрытие без администратора;
- ИИ-ответы без участия человека;
- сложную SLA-маршрутизацию до появления потока обращений.
